# DreamCRM repo conventions

These rules are binding for every agent working in
`https://github.com/DreamCreateWeb/DreamCRM.git` during the Beta-to-1.0 program.
They are not style preferences — a change that violates one gets reverted, and a
few of them protect money, tenant data, or production.

## How to read this rulebook

This file is the map. It carries the five sections short enough to live in it
(§§4, 5, 7, 9, 10) in full, and routes everything else to one file under
`references/`, addressed by its § number — the numbers have not moved, so a

**WHERE THIS RULEBOOK LIVES, AND WHERE YOU EDIT IT (DREAMCRM-109,
2026-09-23).** The files are in the DreamCRM repository under
`docs/rulebook/`, and that is the **authoring surface**: you edit them there,
in a PR, and `test` grades them. What you are reading in the Multica skill
store is a **published copy**. The reason is that a document CI cannot read is
a document nothing can check, and this was the only one here in that position
— nine `STATE:` lines lied about `main` for up to six days, and a cp1252 round

`tests/guards/rulebook-state.test.ts` now fails `test` by name on either.

So: **edit `docs/rulebook/`, open a PR, merge, then publish to the store and
compare BYTES.** Editing the store copy directly makes the graded copy the
stale one. §2 carries the decision, the two options it was taken over, and the
one hop that is still ungraded.

**Open the file your task needs. Do not read them all.** §2 is split four ways
because on its own it was larger than the rest of the rulebook combined, and
almost nobody needs all of it: a UI change needs §2b, a workflow edit needs §2a,
a new guard needs §2d.

## 4. `main` deploys to production

`main` auto-deploys to production via `.github/workflows/deploy.yml`, and database
migrations apply on boot. A merge to `main` is a production release. Treat
anything on that path with extra care and say so in the PR.

CI is the repo's merge gate, not something you sit and watch. Once the merge
commit is on `main`, the deploy belongs to the pipeline — do not poll the run and
do not block your turn on it, unless the issue explicitly asks for the CI or
deploy result.

That rule is about what happens *after* the merge, and it is not a licence to
stop before one. A green local suite plus a PR link is progress, not delivery —
"Delivered means merged" in §3 has the sequence that actually ends a piece of
work.

## 5. Tenant scoping is sacred

- Requests resolve their tenant through `getTenantContext()`.
- Every tenant-scoped query filters on `organization_id`.
- The repo has convention-guard tests enforcing this. If one fails, the query is
  wrong — not the test.

A tenant-scoping mistake leaks one clinic's patient data to another. There is no
"small" version of this bug.

## 7. Changelog policy

Public changelogs are batched **weekly** — one longer entry per week summarizing
shipped work in customer-readable language. Never post a per-update or per-PR
changelog entry to the site.

## 9. Definition of done — you close your own issue

When your issue's deliverables have verifiably landed — PRs merged with the
review gate satisfied where it applies, or the non-code deliverable posted — and
the owner-facing summary is written, **set the issue to `done` yourself**.

- Do not park finished work at `in_review` waiting for the owner to accept it.
- `in_review` means exactly two things: actively awaiting a Sentinel verdict, or
  awaiting an explicitly owner-gated decision. Nothing else.
- An issue whose work is finished and whose summary is posted is `done`, even
  though nobody has replied to it.

This is an owner directive (project rule 4), not a team preference.

**AND DONE MEANS A USER COULD DO THE THING (owner-approved 2026-09-23,
DREAMCRM-119).** Green tests are the floor, not the ceiling. Before you close,
show that the thing a user came for actually works, **evidenced by an E2E
journey or a screenshot on the issue** — the run or the picture, not a sentence
describing either.

This is the third rung of one ladder, and it reads best as a ladder because
each rung was added the day the one below it turned out to be satisfiable while
the work was still broken:

1. **Delivered means merged** (§3) — a green branch is not a delivery.
2. **Green means SERVING** (§2a's rollout verification) — a deploy that built
   and never rolled out is not a release.
3. **Done means a user could do the thing** — a green suite over code nobody
   has driven is not a feature.

**Where the deliverable is not a user-facing change at all** — a guard, a
script, a rulebook edit — the evidence is the one §2d already demands: **the
run where you watched it fail**, named in the issue or the PR. Quote the
assertion that reddened and the reason. The rung does not exempt that work, it
names its evidence; a rung that exempts half the team is the rung nobody
climbs.

## 10. Defects you find in someone else's lane

You will trip over other people's bugs while doing your own work — a flaky spec
that belongs to QA, a backend query behind a UI problem. The rule:

- **It blocks you and you have the root cause — fix it.** A blocked gate is worse
  than a lane boundary. Keep the fix to the defect, tell the owning agent what you
  changed and why, in their issue.
- **Anything else — hand it over with the reproduction.** Name the file and line,
  the failing case, and what you already ruled out. A handoff without a
  reproduction is a rumour, and the owner pays to rediscover it.
- Either way it gets written down. A defect fixed silently in passing is one the
  owning agent cannot learn from, and one nobody adds a regression test for.

**Put the reproduction in the repo, not only in the thread.** Commit it next to
the code or the ceiling it concerns — the baseline entry, the spec, a comment on
the line — with the selectors, the measured values, and why the fix you have in
mind is the right one. The issue thread is where you announce the handoff; the
repo is where the agent who picks it up will actually be standing, and a thread
is not in their editor when they get there. Quinn wrote the booking-page
contrast defect into `e2e/axe-baseline.ts` beside its ceiling — three failing
selectors, their ratios, and why the stronger token was right — and the
cross-lane fix (#548) took minutes instead of an afternoon.

**A contrast hand-off carries the measured foreground hex, the element and the
stop — never only a suspected token.** Vesper's intake, 2026-09-15. Twice this
month a report named a token as the culprit, the named token graded fine, and
the real cause was compositing on top of it; that attribution had pointed nine
baseline entries at a tone that was innocent, while the measured hex found the
real culprit in minutes. A measurement is a fact and an attribution is a guess,
so hand over the fact and let whoever fixes it find the owner.

The same holds for anything you *write down* rather than hand over — an
`e2e/axe-baseline.ts` entry, a `docs/RELEASE.md` Part 5 ledger line, a comment
beside the ceiling. What such an entry owes:

- the **measured foreground hex** and the measured background, as rendered, not
  as specified;
- the **ratio** you measured, not one you computed from the token table;
- the **element** — a selector, not a description — and the **stop** it was
  measured at.

A suspected token is welcome beside those. It is not a substitute for any of
them, and on a surface where compositing, gradients or opacity are in play it is
the part most likely to be wrong — §2's contrast guards exist because the
rendered value and the specified value come apart.

This is a judgement call each time, not a permission slip to work in someone
else's area.
